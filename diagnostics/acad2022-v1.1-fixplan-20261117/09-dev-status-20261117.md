## 四、验收结果（全部为真实 AutoCAD 2022 隔离实测）

### P0-A-1 D8 元数据核查 + 修复 → 通过
见 `01-defects.md` 的 D8 节（已重写）：三个 DXF 方法在运行 DLL 元数据里都在，"装配缺口"是误判；
真因是 INSUNITS 门槛。修复后 `d5fix-03` 导出成功，`$INSUNITS=4` 保留，receipt 记
`insunits=4 / millimetres / disk_readback=4 / coordinate_scaling=none`；负向（全 0 指纹）被拒且不产文件。

### P0-A-2 INSUNITS 只读检查 → 通过
交付图 `三管共用闸阀井_内部评审版V4.dwg` 为 `INSUNITS=4`（毫米），按裁决允许 0/4/6 且不换算。

### P0-A-3 D2 两组受控实验 → 通过，D2 关闭
- **实验 A（拒绝不留 fence）**：`d5fix-03` 提交全 0 指纹的 export plan → `failed / no_effect_terminal`；
  随后 `server.write_fences = 0`、`native.plugin_write_fences = 0`；再提交合法 export plan → `committed_verified`。
  → 拒绝不产生悬挂 fence，也不影响后续写入。
- **实验 B（原 fence 归属不被污染）**：`d2b-02`（`--write --allow-save`，故意不 `--save-to`）
  合法 `set_text` → `committed_verification_pending`、`pending=true`、`write_fence_released=false`，
  `request_jobs` 里 `d2b-02a` 持有 `risk_keys_json=["PATH:F:\...\D2B-02\DR..."]`、`write_fence_released=0`；
  随后提交非法 plan → `rejected_before_submission`，且 **`d2b-02b` 在 ledger 里完全不存在（无行）**。
  → 非法请求既不夺取也不释放原 fence；`stop` 仍返回 `Unresolved write fence: {'native': 1, 'server': 1}`，
  安全阻断按设计生效。
- 结论：D2 是**正常保护**，不是泄漏。关闭，不再继续调查。

### P0-B D5 根因修复 + 真实 CAD 闭环 → 通过（核心成果）

### P0-B 顺带修掉的两个启动缺陷 → 通过
1. `save_drawing` 未纳入启动 reconcile 写入白名单 → 任何 apply+save 后重启都 fail-closed。
   修法：写入分支识别 `FoundationSaveRequest.Plugin` + canonical 校验。
2. 已释放 fence 的行被 `recoveredStage/currentStage` 门槛挡住。修法：加 `releasedStage` 分支，
   行仍由 digest / validator_version / sequence 校验兜住。
   验证：`d5fix-02` 重启后 server 正常 initialize 并进入绑定阶段（不再抛 fail-closed）。
   实测暴露的新错误变成 `drawing_path_mismatch`——即启动 reconcile 已过，卡在图纸身份绑定。

## 六、D6 保存后连续编辑（2026-11-17 最小实现已跑通）

**采用方案 A（稳定工作图纸身份）**，改动三处：
1. `shared\Drawing\DrawingSaveService.cs`：目标路径等于当前文档路径时，改用
   `SaveAs(path, changeFileNames:true, DwgVersion.Current, SecurityParameters)`，
   避免同路径 `SaveAs` 的 `eFilerError`；文档名不变 → 绑定身份不变
2. `client/foundation.py`：新增 `start --reopen`，只允许"已显式 stop（closed-session.json）+ 进程确已退出 + 两端 fence 为 0"的会话在原 owned DWG 上重启，旧 session 归档到 `sessions/`
3. `_tools\update-manifest.py`：连带重算 `client/*` 等所有打包文件摘要（否则改 CLI 后 `Package file changed` 无法启动）

**实测（同一工作区 `p0c-03`，无新建目录）**
```
ROUND 1..5: status=completed effects=committed outcome=committed_verified persisted=True fence=True error=None
```
5 轮 `read → apply(set_text) → apply --save-to <当前图> --overwrite`，全部通过，
`drawing_path_mismatch` 未再出现；第 5 轮文本在第二次重开后仍为 `P0-C 连续修改 第5轮`。
6 条标注在 5 轮修改后测量值不变。

**说明**：`--save-to` 指向另一个路径（交付副本）仍会改变活动图纸路径，属于方案 B（受控 revision 切换），本轮**未实现**；连续编辑请用"就地保存"，交付副本走 DXF 或结束时另存。

**已知观察**：重开后标注的 `entity_digest` 与重开前不同（测量值与样式不变），说明 digest 含重开时会重算的派生字段。它不影响"每次写前重新 read 取新指纹"的正常流程，但**不能把重开前算出的 expected_sha256 用到重开后**。

## 七、当前阻断发布的问题（按优先级）

1. **方案 B 未实现**：`--save-to` 到新路径后，该会话后续任意调用仍 `drawing_path_mismatch`（journal scope 与绑定路径不一致）。需要"保存成功 + 路径与请求一致 + 文件可校验 + 原事务完成"后原子更新 session/revision，属架构级。
2. `apply` 里 `export_dxf`/文件类写入在 `--allow-save` 会话中会留下待持久化 fence，必须再补一次就地保存才 `committed_verified`（当前行为安全但反直觉，考虑改成文件类写入不进入 fence 或自动收口）。
3. 独立 `save` 动作走 apply 通道会被 fence 门拦（`fence_held_by_earlier_unpersisted_write`），实际可用路线是 `apply --save-to` 或客户端 `persist`。
4. **回归未补**：跨 net48/net8 数值哈希兼容回归、"已提交但验证失败"恢复流程用例，尚未入库。
5. 通用 `dwg_export_dxf` 是否加 `expected_insunits`，待两条路径语义对齐。
